## Specs

### S1. Right-Aligned User Message Bubble (80% Column Cap)
User words: "La idea sería copiar bastante, bastante, bastante de la interfaz, o bueno, no la interfaz, sino que toda la parte de chat. El cómo se ve, el cómo tiene las animaciones."
Current fact:
- `.chat-user-row--bubble` in `src/components/views/chat.css` caps width at `720px` instead of `80%` of the transcript column, and does not render inline context chips inside the prose.
Acceptance:
- User messages render as a right-aligned compact bubble (`margin-inline-start: auto`, `width: fit-content`, `max-width: 80%`), using `var(--card-radius)` (`rounded-card`, `12px`), `padding: 10px 14px`, and the surface message token.
- Short messages hug their text and never stretch to 80%. Consecutive user bubbles tighten their shared inner corner using semantic tokens (never arbitrary pixel values).
- Messages exceeding 500 characters or 12 visual lines collapse cleanly with a `Mostrar más` / `Mostrar menos` toggle.
- Hovering or focusing a user bubble reveals a subtle top-right action bar (`Copiar`, `Editar desde aquí`).
- Assistant responses never render inside a bubble; they span the transcript column as left-aligned markdown prose.
Checks: component test in `ChatItemRow.test.tsx` asserting right alignment, `fit-content`, `max-w-[80%]`, and long-message folding.

### S2. Live `Working for` Header and Placeholder `Thinking` Row
User words: "por ejemplo, la parte que nosotros mostramos donde, mostramos que dice 'thinking' y tres puntitos, no me gusta cómo aparece."
Current fact:
- `SingleThreadPane.tsx` and `AgentChatShell.tsx` still mount legacy status rows or keep the placeholder visible after activity rows arrive.
Acceptance:
- While a turn is running, a quiet header row sits at the bottom of the active work block (`TurnActivityStatus` above the composer) with a subtle bottom border (`border-b border-border/60 pb-2 pt-1`), `24px` height (`h-6`), `tabular-nums`, and muted text reading `Working · 12s`. Past 60 seconds the timer reads minutes, as in `Working · 2m 5s`. When there is no start time it reads `Working…`. When compacting context, it reads `Compacting · <timer>` with a minimize icon. The same caption is used in the thread and in the agent chat shell.
- Only one elapsed timer counter is displayed per thread (the bottom `TurnActivityStatus` row). The top thread header (`SingleThreadPane`) displays only the status dot without a duplicate elapsed timer so two counters never drift out of sync.
- The running mark is a 6px status dot with a soft ripple ring that breathes out smoothly over 1.8 seconds (no stepping), in the thread header, the transcript caption, and the thread-list row. The word `Working` stays readable and sweeps a highlight over that color. The clock text stays still and tabular. In the transcript caption a live stage follows the clock (`Working · 1m 6s · Read src/main.ts`, `Thinking`, `Writing`), fades in each time it changes, and is absent until the provider has sent something for the turn. `prefers-reduced-motion` stops both motions and leaves the caption readable.
- It never renders three bouncing dots.
- There is no placeholder brain row. The brain icon and `Thinking` appear only on a reasoning row that already holds thought text; a streaming thought with no text yet renders nothing, and the row shows up the moment the provider sends the first text.
- **Idle Settlement & Turn Sync Guarantees**: While a turn runs and settles, `turnPolling.ts` and `useChatSession.ts` MUST stay synchronized with persisted turn state even across long (`>2m`) runs, transient IPC polling timeouts, HMR/remounts, or active-run transitions:
  - Whenever `readTurnUpdates` returns `resyncRequired: true` while finished, or finishes without delivering terminal events while the thread still holds `status === 'running'` or any `streaming` / `'running'` / `'inProgress'` / `'pending'` item, or when polling aborts/errors, the frontend reconciles immediately against persisted backend state (`loadThreadWithFallback`); mid-turn `resyncRequired` reconciles without terminating an active poller, `status === 'waiting'` approval pauses preserve in-flight items, and normal non-waiting settlement clears stale `streaming` and non-terminal item statuses (`running` / `inProgress` / `pending` -> `'completed'`, or `'failed'` when retry exhaustion or fallback fails) so `.live-tool-shine` and active group labels settle cleanly to `Worked for <duration>` and final assistant responses render without sending another prompt.
  - Transient polling IPC timeouts/errors retry with bounded backoff while the backend turn remains active instead of dropping the poller permanently on the first timeout; active poller tracking keys cleanly by `(threadId, runId)` (never conflating `runId` sets with `threadId` lookups) and re-attaches automatically from `liveRuns` across mounts/navigation, reconciling any thread whose `liveRuns` entry disappears while local state still shows `running`.
Checks: `TurnActivityStatus.test.tsx` verifying the `Working for` timer format, absence of bouncing dots, no `Thinking` at turn start, and the live stage once a tool row arrives; `ChatItemRow.test.tsx` verifying an empty streaming thought renders nothing.

### S3. 24px Work-Log Row Anatomy, Icons, and `live-tool-shine`
User words: "Me gusta bastante cómo manejan como los íconos. Cómo van mostrando las acciones que va haciendo... El cómo se ve, el cómo tiene las animaciones."
Current fact:
- Tool rows in `ChatItemRow.tsx` vary in height and padding, and failed tool rows recolor the entire line or dump raw JSON metadata beneath closed rows.
Acceptance:
- Every work-log row (`ChatWorkEntry`) uses a strict `24px` minimum height (`min-h-6`), `6px` horizontal gap (`gap-1.5`), `14px` font size (`text-sm leading-relaxed`), `var(--control-radius)` (`rounded-md`, `8px`) hover target, and non-selectable label chrome (`select-none`).
- **Icon Slot**: `24px × 24px` (`size-6 shrink-0`) centering a `16px` (`size-4 stroke-2`) muted Lucide glyph (`text-icon-muted`). Both normalized internal tool kinds and ACP `toolKind` values (`read`, `edit`, `delete`, `move`, `search`, `execute`, `fetch`) map to their semantic icons:
  - `Eye` for file read (`Read <relative-path>`, `toolKind: "read"`)
  - `SquarePen` for file edit/write/move/delete (`<relative-path>` or `Changed <path>`, `toolKind: "edit" | "delete" | "move"`)
  - `Terminal` for shell command (`Running <program>` while active; `Ran <program>`, `Failed <program>`, `Declined <program>`, or `Stopped <program>` when finished; `toolKind: "execute"`)
  - `Search` for file/code search (`Searched <query>` or `Searched files`, `toolKind: "search"` or regex-pattern titles)
  - `Globe` for web search/fetch (`Searched the web` or `Fetched <domain>`, `toolKind: "fetch"`)
  - `Hammer` for MCP or dynamic tools (`<server> · <tool> <short-arg>`)
  - `Wrench` for generic tools
  - `Bot` for subagent launches/updates
  - `ListTodo` for plan updates
  - `Brain` for reasoning traces
- **Quiet Trailing Meta**: Line/byte counts (`120 lines · 4.2 KB`) or per-file edit stats (`+18 -4`) sit inline at the end of the `24px` row in muted `tabular-nums`, never on a second line below a closed row.
- **Active Shine**: While a tool row's lifecycle status is `inProgress`, its label text plays `.live-tool-shine` (a `2.2s` smooth highlight sweep across the text; disabled under `prefers-reduced-motion`).
- **Muted Failure Indicator**: When a tool call fails, the row text remains muted secondary text; only the leading `16px` icon turns destructive (`text-destructive`) and a `12px` (`size-3`) `XIcon` appears at the trailing edge.
- **Expandable Inspector**: Clicking a tool or command row smoothly toggles its detail body (`max-h-64 overflow-auto font-mono text-xs select-text rounded-control`), showing the full command, arguments, or live tailing output.
Checks: unit and render tests in `ChatItemRow.test.tsx` for all 10 icon mappings, single-line `24px` geometry, `.live-tool-shine` on active rows, and muted failure styling.

### S4. Streaming Reasoning Preview, Single-Line Live Task Collapse, and Expandable Step Trace
User words: "Quiero que corrijamos o mejoremos una parte de la parte de chat o triad, básicamente. Y algo que es el cómo se muestra la ejecución de las tareas. Me gustaría hacer algo muy similar a lo que hace Anti Gravity. Donde todas las tareas están como... colapsadas, es decir. Se ve una sola línea y se va actualizando de a poquito. Si uno la expande, se va viendo la tarea a tarea. Que va ejecutando la gente, y así."
Current fact:
- Reasoning rows display `Thought for Ns` on individual rows and either hide streaming thoughts or show an unformatted wall of text.
- Work groups previously listed every live step expanded mid-turn and split bursts whenever reasoning items appeared between tool calls.
Acceptance:
- **Reasoning Row**:
  - While reasoning text is streaming and the row is collapsed, it shows the `Brain` icon and the latest thought line, truncated to one line. The preview does not repeat that headline. The status word is `Thinking` only when that line is the whole row. Clicking expands the full markdown reasoning trace (`ReasoningTraceContent`).
  - When a thought item has no text body yet, its label is `Thinking` while active and `Thought` once finished. Individual reasoning rows never say `Thought for Ns`—duration belongs exclusively to the turn summary header.
- **Collapsed-by-Default Single-Line Live Burst & Expandable Step Trace**:
  - Interleaved `reasoning` items inside a tool burst stay grouped inside the same `work` group (`groupTranscriptRows`) instead of splitting the burst; standalone `reasoning` items with no tools remain their own row.
  - Non-rendered or visually-empty transcript entries (`notice` items, empty or settled quiet-turn `note` items, empty/whitespace/protocol-only `assistant` items whose sanitized visible text is empty, empty `reasoning` items, internal dispatch envelopes, and unrendered item kinds) never flush or split a `work` or `subagentGroup` burst and never render empty transcript wrappers (`ChatItemRow`, `ThreadTurnRail`), so live and settled tool/command/reasoning executions remain unified inside one `ChatWorkGroup` until an actual visible interruption (visible `assistant` prose, `user` turn, `error`, visible `note`, `quotaHandoff`, `subagent`, or `swarm` card) appears.
  - Assistant message sanitization (`sanitizeAssistantProtocolText` / `visibleAssistantText` in `chatItemHelpers.ts`) cleanly strips leaked internal role/system-message envelopes (`user\nThe following is a <SYSTEM_MESSAGE> not actually sent by the user... </SYSTEM_MESSAGE>` and standalone `<SYSTEM_MESSAGE>\n[Message] ...` blocks, both complete and unclosed mid-stream, preserving prose mentions like `` `<SYSTEM_MESSAGE>` `` and separating adjacent prose with `\n\n`) and unwraps all `<proposed_plan>` / `</proposed_plan>` tags globally so both persisted conversations and live-streaming turns render cleanly; `turnPolling.ts` handles `"upsert"` and `"delta"` events consistently during live streaming.
  - Both live and settled work groups (`ChatWorkGroup`) render **collapsed by default** as a compact single-line toggle button (`Exploring >`, `Reading output.txt >`, `Editing ChatWorkLog.tsx >`, `Running cargo >` while active, updating progressively to reflect the latest active task with `.live-tool-shine`), with the chevron right-adjacent to the label (`width: fit-content`).
  - Once settled, the collapsed summary reads `Worked for <duration>` / `You stopped after <duration>` alongside the prioritized action summary (`Read 4 files, changed 2 files`, `Ran 3 commands`), or the single step's trace label when non-summarized.
  - Clicking the toggle smoothly expands the work group (`aria-expanded="true"`, rotated chevron) to reveal each individual step (`ChatWorkEntry`) in chronological order—with inline `#L<start>` / `#L<start>-<end>` range badges when present—plus a trailing `Working` status indicator at the bottom while the group is still running.
- **Tool Visibility Modes (`Settings -> Chat`)**:
  - Supports `Show all` (default), `Hide successful` (shows tools while running, keeps only failed ones after completion), `Hide all` (shows only `Thinking` while working), and `Zen` (hides intermediate assistant messages until the final reply). Pending approvals, interactive questions, and errors remain visible in every mode.
Checks: tests in `activityPresentation.test.ts`, `ChatItemRow.test.tsx`, `SingleThreadPane.test.tsx`, and `ThreadTurnRail.test.tsx` verifying progressive live headlines, `#L` line-range badges, collapsed-by-default live bursts, step-by-step expansion with trailing `Working`, interleaved reasoning grouping, unified single-group preservation across non-rendered notices/notes/empty-or-protocol assistant items (while splitting on real visible text), and `Hide all` visibility guarantees.

### S8. Lateral Turn Navigator Rail (`ThreadTurnRail`)
User words: "Cuando se manda un mensaje se va como archivando la zona lateral. Adjunto una imagen. Se va archivando. Y se muestran como distintas pelotitas, cada una de esas es un mensaje que salió, entonces es mucho más fácil volver. A ese mensaje como tal. O a esa parte de la conversación. Por ende debemos, eh, implementar ese componente. Para el chat. Y poder volver a una conversación, a un mensaje rápidamente en una conversación."
Update words: "el componente que muestra la cantidad de mensajes que yo envié al chat. Es decir, ese componente que muestra los puntitos en la zona izquierda del chat. Quiero que se centre... No. Tan abajo. Entonces quiero que esté como a la altura central y ahí, se va agregando los puntos y así."
Current fact:
- Long conversations require manual scrolling to locate earlier user prompts or assistant replies; there is no lateral turn index or quick jump rail.
Acceptance:
- When a thread has one or more user messages (`kind === 'user'`), a compact vertical dot navigation rail (`ThreadTurnRail`) renders vertically centered along the left margin of the transcript body (`SingleThreadPane`, above the composer and changed-files card), expanding symmetrically around the midpoint as new turns are added rather than anchoring near the bottom edge:
  - When turn dots exceed the available rail max height (`min(260px, 100%)`), the dot strip scrolls independently and keeps the active turn dot in view.
  - Each user turn is represented by a circular indicator dot (`rounded-full` / `var(--pill-radius)`).
  - The dot corresponding to the currently visible turn in the transcript viewport is highlighted (`is-active`), while other turns remain muted until hovered or focused.
  - Hovering or focusing a dot displays a floating preview card (`var(--card-radius)`, `12px`) anchored to the right of the rail:
    - **Title**: The user's prompt text for that turn (`font-weight: 600`, clamped to 2 lines).
    - **Preview body**: The assistant's response excerpt for that turn (clamped to 3 lines, plain text without raw markdown markers; falls back to the latest tool/activity summary or `Working…` when no assistant text exists yet).
    - **Footer**: Turn index `"{index} of {total}"` on the left (e.g. `3 of 4`) and formatted message time (e.g. `7:08 p.m.`) on the right in `tabular-nums`.
  - Clicking a dot smoothly scrolls the transcript to that turn's user message (`[data-turn-user-id="<id>"]`) and marks that turn active.
Checks: component tests in `ThreadTurnRail.test.tsx` verifying dot rendering per user turn, hover preview card content (`N of M`, prompt title, assistant excerpt, formatted time), and click-to-scroll behavior.
